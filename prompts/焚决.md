# 焚决：用 Codex 从零开发手机三体模拟器

你是我的开发搭档。请带我从零开发一个实时三体模拟器，逐步加入恒星、粒子、光晕和性能优化，最终在真实手机上运行。

我可能不懂编程。请用容易理解的语言解释必要操作，主动完成你能执行的工作。采用分阶段交付的方式，每阶段都要可以运行，不要一次生成庞大项目后让我自行排错。

## 一、先检查开发环境

开始时，只询问尚未明确的信息：

- 我的电脑系统是什么？
- 目标是 HarmonyOS、Android、iOS，还是先做电脑演示？
- 是否已安装开发工具？
- 是否有测试手机？

默认优先开发 HarmonyOS 版本。检查实际 SDK、编译器和设备连接，不要覆盖无关文件。

涉及平台 API 和厂商加速能力时，查阅官方文档及本地 SDK，不编造接口，不把未接入的能力写成已经生效。

如果暂时无法构建手机应用，先完成跨平台物理核心，并明确尚未验证的手机功能。

## 二、应用目标

开发一个实时三体模拟器：

三颗恒星根据质量、当前位置和速度，在相互引力作用下持续运动；应用实时计算它们的状态，绘制恒星及历史轨迹。

它不是预制轨道动画，也不以跑分为目标。

不要为了画面好看而暗中修改物理结果、强制天体返回或循环播放轨迹。视觉可以艺术化，但必须与物理计算区分清楚。

## 三、物理模型

第一阶段使用牛顿引力、双精度浮点数和 RK4 积分。后续增加带误差控制的自适应 RK45，例如 Dormand–Prince 5(4)。

遵守以下原则：

1. 点质量也有质量。“质点变球体”首先是渲染升级，不代表开始模拟恒星内部流体。
2. 用户界面采用太阳质量、天文单位、地球日等可读单位；内部可归一化计算，但必须正确换算。
3. 近距离相遇时需要控制积分误差，不得随意软化引力来掩盖问题；如果使用软化，必须说明模型变化。
4. 碰撞与逃逸可能是真实物理结果，不能直接认定是算法错误。
5. 通过缩小步长、收紧容差、比较高精度参考解和守恒量判断数值可靠性。
6. RK45 不保证永不碰撞、永不逃逸，也不是辛积分器。
7. 区分碰撞检测使用的物理半径和为了看清而放大的显示半径。
8. 尚未实现碰撞过程时，在检测到表面接触后暂停，并说明原因。
9. 不设置固定60秒结束条件。用户暂停、生命周期变化、物理模型边界或计算异常导致停止时，应显示准确原因。

提供以下预设：

- **八字轨道**：采用有可靠来源的等质量初始条件。
- **随机立体三体**：记录随机种子和完整初始状态，允许碰撞或逃逸。
- **三日交错**：寻找并数值验证一组在有限时间内反复交错、远去后返回的初始条件。

“三日交错”必须实时积分，不能预画轨迹。标明验证时长、算法和误差标准，不承诺永久稳定，也不声称它是小说提供的精确模型。

允许用户自定义每颗恒星的质量、初始位置和初始速度。

## 四、分阶段开发

每阶段完成最小可运行版本，构建并验证后再继续。保留可恢复的阶段版本。

### 第一阶段：基础版

实现：

- 点状恒星。
- RK4 积分。
- 简单线条轨迹。
- 旋转、缩放和复位视角。
- 开始、暂停、继续、重新开始。
- 预设选择及自定义参数。
- 帧率显示。
- 轨迹记录与导出。

“复位视角”只重置相机；“重新开始”才恢复模拟初始状态。

### 第二阶段：粒子版

在第一阶段基础上实现：

- 恒星改为球体，继续使用 RK4。
- 轨迹增加圆形细粒子。
- 粒子沿历史轨迹逐渐变细、变淡，避免整条轨迹粗细一致。
- 粒子仅用于表现轨迹，默认不作为额外天体参与引力计算。
- 全屏黑色背景。
- 底部小横条，上拖逐渐展开控制面板。
- 基础控制和预设放上方，视觉设置、诊断与导出放下方。
- 在支持的设备上申请120Hz输出，不保证跑满120帧。

先定位瓶颈，再决定如何拆分物理计算、粒子数据准备和渲染任务。

避免每帧创建线程、无限增长的任务队列，以及持锁等待GPU。

### 第三阶段：光影版

在第二阶段基础上实现：

- 类似太阳米粒组织、暗斑的程序化表面细节。
- HDR 渲染、亮部提取、模糊和 Bloom 合成。
- 光晕从明亮内圈连续衰减到黑色，避免硬边与明显色带。
- 远离恒星的位置保持黑色，不让整个背景变灰。
- 可在运行中调整的亮度滑块：低亮度看表面，高亮度突出光芒。
- 自适应 RK45，并与 RK4 和电脑参考解比较。

表面效果属于简化视觉模型，不宣称模拟了真实恒星的磁流体活动。

Bloom 不能称为实时光线追踪。

## 五、性能优化

先测量，再优化。

不要看到总CPU使用率低，就认定CPU没有瓶颈；也不要把低帧率直接归因于GPU性能不足。

重点记录：

- 物理计算耗时。
- 粒子与几何数据准备耗时。
- GPU绘制耗时。
- CPU/GPU同步等待。
- 渲染、提交和实际呈现的节奏。
- 温度、设备状态及构建类型。

使用优化构建比较性能，保持场景、相机、亮度、分辨率、模拟进度和加速开关一致。

HarmonyOS 版本可评估 XEngine Kit、Graphics Accelerate Kit 等官方能力，但必须先确认设备、系统、SDK、权限和图形后端是否支持。

每项加速能力保留独立开关及失败回退：

- **超分辨率**：降低内部渲染分辨率后重建画面，说明画质与性能取舍。
- **超帧**：生成中间画面，不改变物理模拟，不把生成帧计入物理计算次数。

不得承诺固定提升比例，收益必须实测。

## 六、帧率统计

严格区分：

- 真实渲染 FPS。
- 包含合成帧的提交 FPS。
- 实际呈现 FPS。
- 屏幕刷新率 Hz。

渲染完成、提交给系统、收到VSync回调，都不等于画面已经显示。

无法取得可靠的实际呈现数据时，明确标注“渲染 FPS”，不得冒充屏幕帧率。

开启超帧后，在左下角增加“含合成提交 FPS”。

约每半秒记录一次帧率，支持导出。暂停时不要继续显示旧的高帧率数值。

通过平台官方机制申请高刷新率，并用外部工具核实。不要通过模拟触摸强行维持高刷新率。

## 七、轨迹导出与验证

导出至少包含：

- 完整初始状态、预设名称和随机种子。
- 单位、引力常数、碰撞半径及其他建模假设。
- 积分算法、步长或误差容差。
- 采样模拟时间。
- 三颗恒星的位置、速度和质量。
- 应用版本与停止原因。

轨迹按模拟时间采样，帧率按真实时间记录，不能混用。

支持电脑离线复算，比较相同模拟时刻的位置、速度、能量、动量和角动量，并检查误差是否随精度提高而收敛。

对于混沌系统，不把长期逐点轨迹一致作为唯一正确性标准。

## 八、工程架构

- 物理核心使用独立 C++ 模块，不依赖手机平台和图形 API。
- 渲染通过抽象接口连接。
- 平台代码独立存放。
- 轨迹、粒子、记录缓存和渲染队列必须有容量管理。
- 暂停、后台切换和窗口销毁时，正确停止任务或释放资源。
- 不将签名证书、密码、设备标识等私人信息加入公开源码。
